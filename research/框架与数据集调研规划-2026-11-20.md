# 固定预算下的自适应多智能体测试：实施与数据规划

日期：2026-11-20。状态：方案和候选选择；尚未下载、运行、核验许可证、生成划分清单或训练模型。与本仓库已有架构衔接，不将其他项目的结果当作本项目结果。

## 1. 研究对象与第一阶段决策

研究问题：相同端到端预算下，按当前状态同时选择测试任务、协作配置及预算，是否比固定和成本感知策略发现更多经独立复现、去重的真实缺陷？测试 agent 是测试工具；被测 app 是系统，区别于交通仿真中的多车 agent。第一阶段建议 **Android GUI + THEMIS + Android 模拟器**，以 ScenGen 为候选多 agent 测试器 / 对照，以 Monkey、DroidBot 及统一接口的单 agent 为对照。选择原因是与现有架构中 ScenGen 的设想一致、真实崩溃缺陷有相对明确的客观证据；不是说它已完成集成或能代表所有软件测试。ScenGen 是移动端框架，不应错误地当作 Web 底座。

保留跨应用测试这一核心泛化目标。首阶段评价的是可复现 crash，不能泛化为业务逻辑、全部缺陷或安全漏洞；数据集小、历史依赖和模拟器架构兼容性可能导致可用样本更少。若受限于资源或复现率达不到门槛，先改用轻量可控测试 fixture 打通框架，再评估 Web 方向，而不是把 fixture 当正式效果结论。

## 3. 实验单位与划分协议

**三层数据**：① 应用/版本/已知缺陷及可运行环境，是 benchmark；② 一次 campaign 含初始 app 状态、可选测试任务池、预算、策略和随机种子；③ 每步状态、动作、成本和结果形成轨迹，是之后价值模型/策略的数据。公开 benchmark 通常不是直接提供调度训练标签，必须在训练应用上自行采集；重复随机种子不产生新应用或新缺陷。

**主划分：按原始项目或上游应用分组**。同项目 fork、相同 APK、同缺陷不同版本、共享源码/复现脚本、派生任务和所有运行轨迹归一组；避免跨集合泄漏。先扫描全部候选的项目 ID、版本、缺陷、权限、可运行性，以预先写好的客观条件过滤并保留全部排除原因；对合格组以固定 seed 分组，目标 60% / 20% / 20%（训练/验证/测试，按应用组数量，必要时按缺陷数、类别和复杂度分层）。这个比例是拟议方案，不是既有官方划分，不承诺可获得具体数量；如类别太少无法兼顾，优先保证项目隔离、报告实际分布，并冻结清单。

- **训练集**：开发 agent/策略、采集随机化轨迹、训练成本/收益模型；只使用训练 app。无模型时直接用规则策略，不为凑数量把测试轨迹并入训练。
- **验证集**：配置、超参、停止条件、预算档位和 prompt 选择；不断比较会造成过拟合，固定评价频次和决策记录。
- **测试集**：方案与数据处理冻结后进行预注册评估，输出全部样本及失败；禁止依据测试结果反复选择策略。已知缺陷、步骤、修复、测试脚本仅评估器可见，不能进入 agent、prompt、检索库或训练数据。测试期可使用所有方法共用的公开产品功能介绍，但不得含缺陷线索；若基准名称或源码/模型预训练造成记忆污染，记录无法排除，并增加时间隔离/新版本分析，不能声称彻底消除。
- 原始 app/版本及派生 bug、初始快照、场景、不同 agent 轨迹都继承 app split。哈希源码、APK 与去重映射，检查 train ∩ val ∩ test 为空；外部数据集同样先做跨集去重。
- `manifest` 计划字段：source、source_revision、app_group_id、app_id、version、apk_sha256、bug_id、bug_provenance、license、environment_image_digest、oracle_id（仅评估侧）、eligibility、reason、split、split_seed。面向 agent 的 manifest 不含 oracle、bug_id 对照表和修复信息。冻结后保存清单 hash；禁止载入秘密 evaluator 目录。

主指标以 app 作为统计聚类单位。THEMIS 体量较小：考虑在冻结正式测试集后，仅对剩余训练/验证项目做分组交叉验证；最终只报告一次保留测试集，置信区间宽时明确结论不稳定。样本数、功效和可行的最小效应须基于试运行方差估计，不能事先宣称显著性。

## 4. 环境与独立验证

每个 campaign 使用独立模拟器/容器和数据目录；记录 emulator/Android/ABI、APK hash、网络规则、时区、语言、权限、设备分辨率、依赖和启动命令。固定或隔离外部服务。比较前从同一干净快照恢复；若模拟器快照不可靠，采用重建/重装和确定性初始化。对至少一个应用两次重置后对比版本、页面、关键数据及复现结果；无法满足的样本记为不可比而非悄悄丢弃。模拟器和模型的非确定性仍需重复试验。

候选证据仅是线索：在干净状态使用 agent 生成的操作序列复现；采集 logcat、包名、异常类型、栈、设备版本和轨迹。由隔离评估器与已知缺陷签名或独立脚本匹配；核查 fixed 版本、同异常栈的其他触发及签名覆盖。复现失败、环境故障、不可判定分开记录；不能仅凭模型判断算确认。去重以标注缺陷 ID 为主，额外未知崩溃按签名聚类并人工复核，单列未知候选。覆盖率只作辅助指标，任务完成不等于发现缺陷。

每次真实测试预算包含搜索、规划、角色沟通、工具调用、重试、复现与验证；集外离线基准验证或人工审核分别单列成本，跨方法一致，不能冒充免费在线验证。测试 evaluator 只负责赛后盲判；在线代理不能访问标签。

## 5. 框架接口与实现顺序

建议 Python 代码，采用小型明确接口而非一开始绑定大型 agent 编排框架：

```text
src/
  core/{types,events,config}.py
  budget/{ledger,admission,pricing}.py
  environments/{base,android}.py
  agents/{base,single,scengen_adapter}.py
  schedulers/{base,round_robin,greedy,cost_aware}.py
  verification/{replay,crash_capture}.py
  data/{manifest,split,trajectory}.py
  runners/{campaign,worker}.py
  analysis/{metrics,report}.py
configs/  manifests/  scripts/  tests/  docs/
```

关键契约：`Environment.reset(snapshot_id, seed)` / `step(action)` / `capture()`；`Agent.propose(observation, quota)`；`Scheduler.choose(state, feasible_actions)`；`Ledger.reserve(id, upper_bound)` / `settle(id, actual)` / `release(id)`；`Verifier.replay(evidence)`。具体实现可调整，但状态、观测权限、事件和版本格式须固定。所有外部调用均通过统一网关；独立的 evaluator 严格隔离。计划支持可重放的追加事件日志，包含 campaign、app group、状态 hash、动作、选择概率、资源预留、实际用量、策略/模型版本、结果及故障原因。

预算先从可严格计数的环境交互次数、模型输入/输出 token 配额和 CPU/设备时长等多维上限开始，明确每一维；可另报告按固定价目计算的估算美元，不把模型调用次数、token、GPU 时间强行相加。允许的动作受多个上限同时约束；若需要单一主轴，预注册一种实际可执行预算并把其他维度作为上限/成本报告。并发预留须原子化；超时、失败、网络重试和进程崩溃均须结算或保留待核对状态。只有服务端可限制输出且调用前能计算输入、最大输出和上界时，才能主张相应单位硬约束；API 计费不透明或工具无法停止时只报告软预算与超支。

阶段门：
1. **P0 清单审计**：下载前查许可证及资源；清点 THEMIS 样本、ScenGen 角色及运行依赖，发布纳入/排除台账与固定版本。
2. **P1 可复现性**：训练候选中至少 2 个不同 app 各完成基准官方已知缺陷复现、清理和重复复现；核验 scorer 隔离。这个阈值仅作为工程启动门槛，不代表正式样本量。
3. **P2 最小闭环**：一个本地 fixture 与一个真实 app 接通单 agent、预算、证据、复现、日志；断点、并发、超额、失败等关键账本行为做有意义测试。
4. **P3 对照接入**：原始 ScenGen、单 agent、Monkey/DroidBot 根据可用性接入或记录不可复现原因；预算、观测、设备、任务池、检查器统一，保留原方法与修改说明。
5. **P4 划分冻结与采集**：按组建立清单并进行泄漏审计；仅训练应用运行探索策略。对可恢复状态，以随机化顺序分配候选动作并记录选择概率，记录后续策略和全成本。重复执行不自动提供反事实因果真值。
6. **P5 模型与评估**：先规则策略、成本估计和简单回归排序；只有样本、覆盖度和验证表现足够时再考虑图模型、离线策略学习或前瞻。验证集确定方案后运行冻结测试。

## 6. 公平实验与报告

至少比较：固定单 agent + 均匀预算；固定多 agent + 均匀预算；单 agent + 动态分配；多 agent + 动态分配（2×2）；以及在可行候选中按历史收益/成本的朴素成本感知基线和随机策略。每个基线必须明确使用相同可见信息、候选动作和任务、在线验证能力、工具与总预算；结构性例外必须说明。固定模型版本、提示词、截图/层级访问权限，避免把强模型或工具差异归因于调度。按 app、初始状态、预算、随机种子配对，方法顺序随机化；因 app 为聚类单元计算配对差值和 app 级 bootstrap 区间，报告每 app 效果及失败。

主要结局：预算内独立确认且按缺陷去重的数量及发现率，分母是可评价已知缺陷或应用，明确两者；同一缺陷重复发现只算一次。辅以预算—发现曲线、有效执行数、验证率、复现成功率、误报/不可判定数、token、模型账单、设备时间、计算与调度开销、超支率。设置多个预注册预算档；报告完整成本曲线，包含无发现、环境失败和超时。跨 app 汇总、按难度/类别分层和资源消耗分开呈现，不将多随机种子当独立项目。论文结论不得超出 crash 数据、样本量和环境。

## 7. 当前未决与首批工作

- 本次没有安装或运行任何基准，THEMIS 可下载性、设备 ABI、实际有效样本、ScenGen 改造难度、复现 oracle 和许可证都未验证；候选选择受 P0/P1 门槛约束。
- 训练/验证/测试尚没有实际名单；只能在应用清点、去重和可运行性筛查后生成、审计和冻结，不能凭空宣布比例落实。
- 机器可用内存、模拟器架构、GPU、可接受 API 预算和是否需要纯本地模型会影响执行参数；不阻碍先做只读盘点。
- 下一步以 P0/P1 为起点，生成资产与许可证清单，核对本机资源和基准兼容性；通过后再实现 P2 最小闭环，而不是先实现图网络或强化学习。
